# Sandbox security boundary

Coding tools execute in a dedicated Python 3.12 Docker image as uid/gid 10001. The container has `--network none`, a read-only root filesystem, a small temporary `/tmp`, one writable labeled volume at `/workspace`, `--cap-drop ALL`, `no-new-privileges`, and configured CPU (1), memory (512 MiB), PID (128), and command-time limits. It is not privileged, has no Docker socket, and does not share host PID or network namespaces. Only the trusted Continuum executor control plane can ask the host Docker daemon to create/remove sandboxes; the sandbox itself cannot control Docker. This is a significant privilege on the **executor**, so deploy that component only in a trusted local environment.

The fixed sandbox tool accepts explicit JSON operations. It does not run model-provided shell strings. File paths are centrally normalized, absolute paths and `..` are rejected, `.git` internals are excluded, and resolved symlink targets must remain beneath `/workspace`. File reads, searches, patch size, result count, output and execution time are bounded. Git subprocesses disable hooks and global/system configuration and have a timeout. Tests run fixed `python -m pytest` argv with plugin autoload and bytecode writing disabled. Fixture checkout needs no network. No arbitrary remote clone or dependency installation is offered.

These controls address accidental host filesystem access, traversal/symlink escape, direct host command execution, unbounded tool output, and runaway test commands. Published Compose development ports bind to `127.0.0.1` by default; changing `DEV_BIND_HOST` to a public interface exposes unauthenticated development APIs and default database credentials. Real Docker integration tests inspect actual container HostConfig and mounts; path tests exercise traversal, absolute and symlink escapes.

They do **not** establish hardened containment for deliberately hostile code, kernel/container escape resistance, multi-tenant cloud isolation, supply-chain safety, or safety of future network-enabled dependency downloads. Python tests inside the sandbox can run arbitrary code within that container and writable workspace volume. The API approval endpoints have no authentication and must not be exposed publicly. Before accepting untrusted repositories or users, add a stronger sandbox boundary (for example rootless/VM isolation), host Docker control-plane isolation, artifact scanning, authorization, and a strict network/package policy.
